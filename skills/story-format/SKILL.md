# 유저 스토리 & 사양서 작성 가이드

## 유저 스토리 형식

전체 템플릿: [story-template.md](references/story-template.md)

### 스토리 포맷 종류

| 포맷 | 구조 | 적합한 상황 |
|------|------|------------|
| Classic | As a [role], I want [feature], so that [benefit] | 사용자 대면 기능 (로그인, 검색, 프로필) |
| Job Story | When [situation], I want to [motivation], so I can [outcome] | 컨텍스트/상황 중심 (알림, 오류 복구) |
| FDD | [Action] the [result] [by\|for\|of\|to] a(n) [object] | 기술/인프라 작업 (DB 마이그레이션, API) |
| Problem-Goal | Problem + Goal statement | 복잡한 도메인 문제 (알고리즘 개선) |

기본값: Classic. 상황에 따라 가장 적합한 포맷을 선택한다.

### 핵심 구조 (Classic)

```markdown
# US-{NNNN}: {동사형 제목}

## Story
**As a:** {구체적 페르소나 — "사용자"가 아닌 역할+맥락}
**I want to:** {원하는 행동}
**So that:** {달성하려는 가치 — 사용자에게 의미 있는 결과}
```

**Negotiable 원칙**: "I want to"는 **결과**를 기술하되, **구현 방법을 지정하지 않는다.**
- ❌ "React 컴포넌트를 사용하여 프로필을 표시한다"
- ✅ "내 프로필 정보를 확인할 수 있다"

### 핵심 구조 (Job Story)

```markdown
# US-{NNNN}: {동사형 제목}

## Story
**When:** {상황/트리거 컨텍스트 — 사용자가 처한 구체적 상황}
**I want to:** {동기 — 사용자의 내적 목표. 행동이 아님!}
**So I can:** {기대 결과/가치}
```

**주의**: "I want to"는 **동기(motivation)**이지 **행동(action)**이 아니다. 행동은 negotiable.
- ❌ "I want to: 택시를 부른다" (행동 — 구현을 제한)
- ✅ "I want to: 이동 시간을 최소화한다" (동기 — 택시/우버/달리기 모두 가능)

### 핵심 구조 (FDD / Problem-Goal)

FDD: `[동사] the [결과] [by|for|of|to] a(n) [대상]`
Problem-Goal: Problem 섹션 + Goal 섹션으로 구성

### INVEST 기준 검증

모든 스토리는 작성 후 INVEST 기준으로 검증한다:

| 기준 | 질문 | 미충족 시 |
|------|------|----------|
| **I**ndependent | 독립적으로 구현 가능한가? | 의존 관계 명시 또는 분리 |
| **N**egotiable | 구현 방법이 유연한가? | AC에서 구현 상세 제거 |
| **V**aluable | **사용자에게** 가치를 전달하는가? | "So that" 절이 사용자 가치를 표현하도록 강화 |
| **E**stimable | 추정 가능한 크기인가? | 스파이크 제안 또는 SPIDR 분할 |
| **S**mall | 한 Sprint에 완료 가능한가? | SPIDR 분할 제안 |
| **T**estable | 자동화 테스트를 작성할 수 있는가? | AC의 Then을 구체적/측정 가능하게 |

**Valuable 주의**: "So that 개발자가 X를 구현할 수 있다"는 사용자 가치가 아님. 사용자 관점의 가치를 기술해야 한다.

### 스토리 포인트 스케일

| 포인트 | 의미 |
|--------|------|
| 1 | 매우 간단. 설정 변경, 텍스트 수정 수준 |
| 2 | 간단. 단일 컴포넌트 수정 |
| 3 | 보통. 2-3개 파일 수정, 새 컴포넌트 1개 |
| 5 | 복잡. 여러 컴포넌트, API 연동 |
| 8 | 매우 복잡. 새 시스템 구성요소. 분할 검토 |
| 13 | 에픽 수준. 분할을 강력히 권장 |

## Acceptance Criteria (AC) 작성 규칙

### AC 개수 가이드

| 상황 | AC 개수 | 비고 |
|------|---------|------|
| **최소** | 3개 | 해피 패스 + 에러 케이스 2개 |
| **일반적** | 5~8개 | 주요 경로 + 예외 + 경계값 |
| **레드 플래그** | 10개 이상 | 스토리가 너무 크다는 신호 → 분할 검토 |

### Given/When/Then (Gherkin) 형식

```markdown
### AC-1: {시나리오명}
- **Given:** {사전 조건}
- **And:** {추가 조건 — 복합 조건일 때}
- **When:** {사용자 행동/트리거}
- **And:** {추가 행동 — 다단계일 때}
- **Then:** {기대 결과}
- **And:** {추가 결과 — 단일 결과에 부수 효과가 있을 때}
- **But:** {예외 — 발생하지 않아야 할 것}
```

**예시: 로그인 기능의 AC들**

```markdown
### AC-1: 유효한 자격증명으로 로그인
- **Given:** 사용자가 로그인 페이지에 있다
- **And:** 활성화된 계정이 존재한다
- **When:** 올바른 이메일과 비밀번호를 입력하고 제출한다
- **Then:** 대시보드 페이지로 이동한다
- **And:** 세션 토큰이 생성된다

### AC-2: 잘못된 비밀번호
- **Given:** 사용자가 로그인 페이지에 있다
- **When:** 존재하는 이메일과 잘못된 비밀번호를 입력한다
- **Then:** "자격증명이 올바르지 않습니다" 에러 메시지가 표시된다
- **But:** 페이지가 리다이렉트되지 않는다

### AC-3: 계정 잠김 (5회 실패 후)
- **Given:** 사용자가 4회 연속 로그인에 실패했다
- **When:** 5번째 잘못된 비밀번호를 입력한다
- **Then:** 계정이 30분간 잠긴다
- **And:** "계정이 일시적으로 잠겼습니다" 메시지가 표시된다
```

### AC 작성 원칙

- **Then은 검증 가능**해야 한다 — 자동화 테스트를 작성할 수 있어야 함
- **다중 Then**: 단일 행동의 부수 효과일 때만 사용. 별개의 행동이면 별도 AC로.
- **AC는 결과(What)**를 기술하고, **구현(How)**을 지정하지 않는다

### AC 안티패턴

| 안티패턴 | 예시 | 개선 |
|---------|------|------|
| 주관적 표현 | "직관적이어야 한다" | "5클릭 이내에 완료" |
| 측정 불가 | "빠르게 응답한다" | "200ms 이내 응답" |
| 구현 지정 | "Redis에 캐싱한다" | "2초 이내 응답" |
| 일반적 페르소나 | "As a user" | 구체적 역할+맥락 |
| 에러 케이스 누락 | 해피 패스만 | 최소 2개 에러/예외 AC |
| AC에 DoD 포함 | "코드 리뷰 완료" | DoD는 팀 전체 규칙 (아래 참조) |

## Definition of Done (DoD) vs Definition of Ready (DoR)

### DoR (스프린트 진입 전)

스토리가 스프린트에 포함되기 전 충족해야 할 조건:

- [ ] 스토리가 템플릿 형식을 따른다
- [ ] INVEST 기준 모두 충족 (✅)
- [ ] AC가 명확하고 테스트 가능하다
- [ ] 의존성이 식별되었다
- [ ] 추정 가능한 크기이다 (13pt 이하)
- [ ] 미해결 질문이 없다

**모두 충족**: Status = `pending` | **미충족**: Status = `draft` (미충족 사유 명시)

### DoD (구현 완료 기준)

**모든 스토리에 공통으로 적용되는 팀 품질 기준.** 개별 스토리 AC와 별개.

- [ ] 모든 AC가 충족되었다 (테스트 통과)
- [ ] 코드 리뷰 완료
- [ ] 단위 테스트 작성 및 통과
- [ ] 기존 테스트가 깨지지 않았다 (회귀 없음)
- [ ] 문서 업데이트 (필요 시)
- [ ] 스테이징 환경에 배포 가능

**AC ≠ DoD**: AC는 "이 스토리가 하는 것", DoD는 "모든 스토리가 만족해야 할 품질 기준".

## SPIDR 스토리 분할

스토리가 너무 클 때 (8pt 이상, 또는 Small/Estimable 미충족) 5가지 차원으로 분할:

| 차원 | 질문 | 예시 |
|------|------|------|
| **S**pike | 미지의 영역이 있는가? | "OAuth 연동 가능성 조사" 스파이크 생성 |
| **P**ath | 대안 경로로 나눌 수 있는가? | 해피 패스 / 에러 처리 / 관리자 플로우 |
| **I**nterface | 채널/플랫폼별로 나눌 수 있는가? | 웹 / 모바일 / API |
| **D**ata | 데이터 범위를 줄일 수 있는가? | 텍스트만 → 이미지 추가 → 동영상 추가 |
| **R**ules | 비즈니스 규칙을 단계적으로 적용할 수 있는가? | 기본 검증 → 고급 검증 → 실시간 검증 |

분할 원칙: 각 분할된 스토리가 **독립적으로 가치를 전달**해야 한다 (수직 슬라이싱).
안티패턴: UI와 백엔드를 별도 스토리로 분할하는 것 (수평 분할 — 개별 가치 없음).

### Example Mapping

복잡한 스토리 정제 시 사용하는 구조화 기법 (Matt Wynne):

- **Story** (Yellow): 스토리 자체
- **Rules** (Blue): 수용 기준/비즈니스 규칙
- **Examples** (Green): 각 규칙을 설명하는 구체적 예시
- **Questions** (Red): 미해결 질문

Red 카드가 남아 있으면 스토리는 **Ready가 아니다** (draft 상태).

## 기술 사양서 형식

전체 템플릿: [spec-template.md](references/spec-template.md)

### 핵심 구조

```markdown
# SPEC-{NNNN}: {제목}
> Based on: US-{NNNN} — {스토리 제목}

## 1. Overview
## 2. Changes (New Files / Modified Files)
## 3. Interfaces / API Contract
## 4. Data Model
## 5. Implementation Order
## 6. AC Mapping (AC → Test Approach → Pass Criteria)
## 7. Edge Cases
## 8. Security Considerations
```

### 사양서 품질 기준

- 모든 파일 경로는 프로젝트 루트 기준 실제 경로
- 인터페이스는 타입/시그니처 명시
- **AC 매핑은 1:1** — 스토리의 모든 AC가 사양서에 매핑되어야 함. 누락 불가.
- AC 수가 스토리와 불일치하면 경고 반환
- 구현 순서는 의존성 기준으로 정렬
- 코드베이스 분석 결과 반영 (기존 패턴 준수)
